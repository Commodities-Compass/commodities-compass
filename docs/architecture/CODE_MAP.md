## How data flows, in one paragraph

Every weekday after market close (**Phase A**, ~18:30–19:15 UTC), scrapers write raw market data into `pl_contract_data_daily` (OHLCV+IV, keyed on `(date, contract_id)`), into the weekly/quarterly cadence tables (`pl_stock_observation`, `pl_cot_eu_weekly`, `pl_cot_us_weekly`, `pl_supply_demand_observation`), and into the shared external table `pl_external_indicator` (FX daily, ENSO monthly). The **indicator engine** (`compute-indicators`) then reads `pl_contract_data_daily`, computes 26 derived indicators → `pl_derived_indicators`, applies 5-day smoothing + rolling 252-day z-scores, runs the power-formula composite, and writes scores + decision into `pl_indicator_daily` (+ per-indicator decomposition into `pl_signal_component`) **and** the algorithm-independent `pl_dashboard_gauge`. On the **eve of the next trading day** (**Phase B**, gated by `is_eve_of_trading_day()`), the agents fire: meteo + press review write fundamentals (`pl_weather_observation`, `pl_fundamental_article`, `pl_article_segment`); then **`cc-regime-shadow`** runs the served decision in one execution and three steps — L1+L2 regime (self-computing its features from raw prices, it never reads `pl_derived_indicators`) → `pl_regime_shadow`, L3 judge (o4-mini macro overlay reading press + weather from the DB) → `pl_judge_shadow`, and the **adapter row** that projects the fused call into `pl_indicator_daily`, structural only. **`cc-regime-brief`** then writes the prose — natively per language, not translated — onto that same row and uploads the `.txt` to Google Drive for NotebookLM audio. Finally `cc-publish-session` flips the dashboard atomically once data and audio are both ready. The **FastAPI dashboard** reads only `pl_*` tables, resolves the user's calendar `display_date` back to a session `date`, picks the active contract (handling rolls) and walks `pl_algorithm_version.serving_rank` to decide which algorithm answers. Every row is keyed to a **session date** and a **contract_id**; the dashboard's `display_date` (= next trading day) is the only place that offset lives.

## Subsystems

### 1. Indicator computation engine — `backend/app/engine/`
Production Python pipeline that replaced the Google Sheets formula engine: 14 indicators → 26 derived columns, 5-day SMA smoothing, rolling 252-day z-scores, power-formula composite with two-pass momentum → OPEN/HEDGE/MONITOR. Contract-centric, config-as-data.
- **Entrypoints**: `runner.py` (CLI `poetry run compute-indicators [--all-contracts|--contract CAK26] [--dry-run|--full] [--algorithm legacy --algorithm-version 1.0.1]`), `pipeline.py` (orchestrator), `registry.py` (topo-sort), `composite.py`, `normalization.py`, `smoothing.py`, `db_writer.py`, `indicators/`, `types.py`. See `app/engine/README.md`.
- **Reads**: `pl_contract_data_daily`, `ref_contract`, `pl_algorithm_version`, `pl_algorithm_config`. **The series loaders deliberately do NOT join `pl_indicator_daily`** — `macroeco_bonus` is merged per algorithm version inside `_run_for_version`, because that table is keyed `(date, contract, version, language)` and joining it on `(date, contract)` fanned the OHLCV series out 2-5× and silently corrupted every rolling indicator (PR #74, timeseries-uniqueness).
- **Writes**: `pl_derived_indicators`, `pl_indicator_daily`, `pl_signal_component`, `pl_dashboard_gauge` (the gauge stage is algorithm-independent and re-runnable alone via `--stage gauges`).
- **Docs**: `flows/indicator-engine.md` (planned) · `app/engine/README.md`.
- **Key invariants**: rolling 252-day z-score over **session date** (never `display_date`) — replaces Sheets full-history look-ahead bug; two-pass momentum (base score with momentum=0 first); `pl_signal_component.raw_value`/`normalized_value` must trace to a computation, never literals (pipeline-continuity); config (16 coeff/exp pairs, k, thresholds) loaded from `pl_algorithm_config`, `LEGACY_V1` is fallback only; idempotent upsert on `(date, contract_id[, algorithm_version_id])`; warmups EMA26=26, MACDSignal=35, RSI=15, Stoch/ATR=14, Bollinger=20.

### 2. Models & migrations — `backend/app/models/` + `backend/alembic/versions/`
SQLAlchemy ORM + 38 Alembic migrations defining the contract-centric `pl_*`, reference `ref_*`, and audit `aud_*` schema. The bridge between typed Python models and the PostgreSQL 15 prod schema.
- **Entrypoints**: `models/pipeline.py`, `reference.py`, `signal.py`, `audit.py`, `test_range.py`, `base.py`; legacy (`technicals.py`, `indicator.py`, `market_research.py`, `weather_data.py` — present for audit, unused by prod). Migrations in `backend/alembic/versions/` (e.g. `n8i9j0k1l2m3_create_v_contract_data_chained.py`, `r2m3n4o5p6q7_stocks_cot_us_dedicated_tables.py`).
- **Reads/Writes**: all `pl_*` / `ref_*` / `aud_*` tables + `test_range` (schema authority for every other subsystem).
- **Docs**: `flows/schema.md` (planned) · `.local`/HEDI_DATA_MAP for column-level detail.
- **Key invariants**: `display_date = next_trading_day(session date)`; only `pl_contract_data_daily` carries `display_date`, all other `pl_*` use session `date` only. Weekly/quarterly cadence tables (`pl_stock_observation`, `pl_cot_*_weekly`, `pl_supply_demand_observation`) keyed on `report_date`, never stamped daily. `GENERATED` columns (`prod_merc_net`, `m_money_net` on both COT tables) are never written directly. **Migrations reach prod via `main` only** (migrations-prod-via-main-only); idempotent UP/DOWN (`_has_column` / `IF NOT EXISTS`).

- **Docs**: `flows/dashboard-request.md` (planned) · § "API Structure" + "Google Drive Audio Integration" in CLAUDE.md.

### 4. Services — `backend/app/services/`
Business-logic layer behind the endpoints: position/decision, YTD, indicator gauges, recommendations, news, weather enrichment, audio metadata, COT/stock positioning, macro panel, farmgate price, CSV export, WatchAI origin flows, **judge diagnostics**. All reads, no writes.
- **Entrypoints**: `dashboard_service.py` (+ `dashboard_transformers.py`), `audio_service.py` (Google Drive singleton), `positioning_service.py`, `macro_panel_service.py`, `weather_service.py`, `farmgate_service.py`, `export_service.py`, `origin_flow_service.py` + `origin_balance.py`, `judge_diagnostics_service.py`. `ensemble_diagnostics_service.py` was **deleted 2026-08-19**.
- **Reads**: same `pl_*` set as the API layer (contract-centric); legacy `Technicals`/`Indicator` never imported.
- **Docs**: `flows/services.md` (planned).
- **Key invariants**: contract-per-date resolves through the roll calendar — `resolve_contract_for_date()` is a thin wrapper over `front_month_for_date_or_none()`, and `v_contract_data_chained` is a calendar INNER JOIN on `ref_contract.active_from` (no OI/volume); position defaults to MONITOR on null (benign) but logs ERROR on unrecognized values (never silent corruption); YTD + running-accuracy use `eval_horizon_for(algorithm)` — **regime is scored J+1**, everything else falls back to `YTD_EVAL_HORIZON_DAYS=4`; contract/algo lookups cached 5min, audio lookups 1h hit / 5min miss; judge diagnostics stay silent (not fabricated) on a date the overlay did not run, and `rationale` — the fuse trace — is deliberately **absent from the payload**, not merely unrendered.

### 5. Core & utils — `backend/app/core/` + `backend/app/utils/`
Infrastructure: Pydantic config, Auth0 JWT validation (JWKS cached 6h), dual DB engines (async for FastAPI, sync for Alembic/scripts), slowapi limiter, Sentry init; utils for contract/algorithm resolution, date parsing, trading calendar, type converters.
- **Entrypoints**: `core/config.py`, `core/auth.py`, `core/database.py`, `core/rate_limit.py`, `core/sentry.py`; `utils/contract_resolver.py` (async — `REGIME_VERSION_NAME = "regime"`, `ENSEMBLE_VERSION_NAME`, `LEGACY_VERSION_NAME`; the names are constants, **which one is served is `serving_rank`, never a code path**), `utils/serving_chain.py` (walks the rank), `utils/front_month.py`, `utils/date_utils.py`, `utils/trading_calendar.py`, `utils/converters.py`.
- **Reads**: `ref_contract`, `pl_algorithm_version`, `pl_indicator_daily`, `pl_contract_data_daily`, `ref_exchange`, `ref_trading_calendar`.
- **Docs**: `flows/resolution.md` (planned).
- **Key invariants**: `async_engine` → FastAPI only, `sync_engine` → Alembic/scripts only (mixing deadlocks the loop); 4-tier contract fallback always yields a `contract_id` (no gaps across rolls); `PlIndicatorDaily` keyed `(date, contract_id, algorithm_version_id)`, no retroactive ensemble backfill; TTLCache auto-expires (5min resolver / 6h JWKS), no manual invalidation — scrapers in other processes see stale `contract_id` until TTL (acceptable, rolls are rare). **Note**: `app/utils/contract_resolver.py` (async) and `scripts/contract_resolver.py` (sync) are two separate modules — never mix in one process.

### 15. Per-client entitlement & tenancy — `backend/app/core/{entitlements,tenancy,audio_signing}.py` + `backend/app/models/tenant.py`

- **Reads**: `tenant_account`, `tenant_user`, `v_tenant_entitlement_current` (from `tenant_entitlement`). Writes are CLI-only (append-only grants/tombstones).

### 16. WatchAI origin flows (matrix block ②) — `backend/scripts/watchai_sync/` + `backend/app/services/origin_*.py` + `backend/app/models/origin.py`
Côte d'Ivoire **physical** origin flows: customs export declarations, exporter purchases, GEPEX grindings. Unlike every other subsystem here there is **no Cloud Run job and no scheduler** — ingestion is a manual CLI run by a human against a `watch-ai` checkout, because the upstream is a set of files, not an API. Serves Section VI "Marché physique" of the dashboard.
- **Entrypoints**: `poetry run watchai-sync --source <watch-ai checkout> [--dry-run] [--target {local,prod}] [--skip-compute]` and `poetry run map-exporter` (benchmark identity, hand-reviewed). Serving: `app/services/origin_balance.py` (pure bean-equivalent arithmetic, no I/O) + `origin_flow_service.py` (queries) → `api_v1/endpoints/origin.py` (`/dashboard/origin/{campaign,market-views,destinations,exporters,benchmark}`), one entitlement key per matrix row.
- **Tenancy seam**: the benchmark is the only per-tenant view. Identity lives on `tenant_account.exporter_entity_id` and is applied **at read time** — never a column on the cube, which stays tenant-free ("pipelines shared, tenants subscribe").
- **Writes**: `pl_origin_export_declaration`, `pl_origin_purchase_monthly`, `pl_origin_grinding_monthly` (facts), `ref_origin_entity` (exporter registry — `ref_` namespace, not `pl_`), `pl_origin_flow_monthly` (the cube), `pl_origin_ingest_batch` (audit trail). Migration `n9c0d1e2f3g4`.
- **Reads**: only its own tables. It touches **nothing** in the daily pipeline — no `pl_contract_data_daily`, no `pl_derived_indicators`, no contract at all. Origin flows are monthly and commodity-level; the rest of the app is daily and contract-keyed.

- **Key invariants**: the material balance is **bean-equivalent** — transformed exports go back through `÷ RENDEMENT_BROYAGE (0.80)` before entering it; adding them raw is the v1 double-count (124 % outflow). STATSER grindings are **derived and confronted, never an input**, and the confrontation is computed **GEPEX on both sides** (`perimeter` is a required non-defaulted kwarg). **`solde ≥ 0` is NOT an invariant** — 2021-2022 legitimately reaches 108,1 %; it is the publishable flag `outflow_exceeds_purchases`, never a 500. YTD is a **month-set intersection per source**, each with its own window (grindings trail 2-3 months). Batch identity is a **content hash** of the source files, not a commit SHA.

## Load-bearing invariants (cross-subsystem — break these and prod breaks)

1. **Contract roll — the roll CALENDAR is the source of truth (the big one).** Since `d5e6f7a8b9c0` (PR #73), front-month for date D = the `ref_contract` row with the greatest **`active_from <= D`**. One rule, three agreeing implementations: `app/utils/front_month.py` (async), `scripts/front_month.py` (sync), and the **`v_contract_data_chained`** VIEW — a **calendar INNER JOIN**, no OI/volume anywhere. It *follows* the stamp, it never leads it. `is_active` is a derived cache (still read by the barchart scraper, intraday monitor, press-review agent, dashboard no-date fallback) and must stay in sync, but it does not move the front-month. Liquidity decides nothing: it survives only in `cc-roll-watchdog` as a Sentry nudge. `resolve_contract_for_date()` is now a thin calendar wrapper — the 4-tier cascade is gone; `resolve_active_at_date()` is deleted. ⚠️ INNER JOIN ⇒ **a date whose calendar front-month has no OHLCV row disappears silently** (all jobs exit 0) — so `poetry run roll-contract <NEW>` (the only writer of `active_from`) must run on a weekend or after 19:10 UTC, never mid-session, and never be replaced by a raw `UPDATE … SET is_active`. **A new consumer must resolve through `front_month.py` or the VIEW — never a fixed code, never its own heuristic.** (See `docs/runbooks/contract-roll-procedure.md`, memory `feedback_no_hardcoded_contracts`.)

2. **Session date vs `display_date`.** `pl_contract_data_daily.date` = session date (immutable trading day, what every `pl_*` row and all computation key on). `display_date = next_trading_day(date)` exists **only** on `pl_contract_data_daily` and is the value the frontend calendar shows. Resolution is always `display_date → session_date`, never reverse. No `-1 day` offset in the frontend.

3. **P2b two-phase date keying.** Phase A (market close, weekday) writes session `date = T`. Phase B (eve of next trading day, daily cron + `is_eve_of_trading_day()` gate) frames prompts/filenames on `target_date` (= next session) but keys **every DB write** to `data_date = get_previous_session_date(target_date) = T`. This keeps `pl_indicator_daily` / `pl_fundamental_article` / `pl_weather_observation` / `pl_orchestrator_decision` all on a single session date the dashboard can resolve. Violating it = empty dashboard sections the next morning (PRs #15–#17, #35).

4. **Migrations reach prod via `main` only.** Never `alembic upgrade head` against GCP Cloud SQL from a feature branch. DB prod revision must never be ahead of `main` (a cold-start `alembic upgrade head` then crashloops). Local DB: any branch is fine. (migrations-prod-via-main-only.)

5. **Pipeline continuity — no invented values.** DB writers receive computed values; they never hardcode a literal where a computation belongs. `pl_signal_component.raw_value` ≠ `normalized_value` (two sources). Missing computed value → NULL, never 0.0. (pipeline-continuity.)

6. **Fail loud, no silent recovery (producers).** Pipeline producers (scrapers, agents, compute jobs) exit non-zero + Sentry on any error — no auto-retry, no provider fallback, no partial output. Recovery = diagnose → fix root cause → manual relaunch. Consumers (dashboard, briefs) MAY degrade gracefully on missing upstream data. (pipeline-error-handling.)

7. **`serving_rank` decides what is served — an integer, not a code path.** `pl_indicator_daily` is keyed `(date, contract_id, algorithm_version_id)`. The dashboard walks `pl_algorithm_version.serving_rank` ascending and takes the first algorithm that has a row for that date: `regime = 1`, `ensemble = 2`, `legacy = 3`. Ranks 2 and 3 are **historical links only** — those tracks stopped writing on 2026-08-18 — so they answer for old dates and never for a current one. The rank designates a *name*, not a row; two partial unique indexes (`uq_algorithm_serving_rank`, `uq_algorithm_serving_name`) keep it unambiguous. NULL rank = never served.

8. **Config-as-data.** Algorithm coefficients/thresholds, wrapper levers, macro-gate cap live in `pl_algorithm_config` rows — flip without redeploy. Hardcoded `LEGACY_V1` is fallback only. `GENERATED` columns (COT net positions) are never written directly. (north-star-alignment.)

9. **Engine math correctness.** Rolling 252-day z-scores over session date (not full-history — fixes Sheets look-ahead); Wilder RSI/ATR; symmetric Bollinger; two-pass momentum (base first). **The scoring horizon is per algorithm, no longer uniform**: `eval_horizon_for(name)` returns J+1 for `regime` (it decides for the next session) and J+4 otherwise. A single hardcoded horizon would score the served track on a window it never claimed.

12. **One row per time step in any series loader.** Any query feeding a rolling / recursive / positional computation must return exactly one row per `(date, entity)`, asserted at the boundary (`_assert_unique_dates`). A `LEFT JOIN` onto a table with a wider unique key fans the series out and corrupts every EMA/RSI/ATR/z-score downstream **with no error** — and the upsert on `(date, contract)` then makes the stored table *look* clean. This went unnoticed for months (PR #74). Prefer keeping the multi-keyed table out of the loader entirely over filtering it. (timeseries-uniqueness.)

10. **Async/sync engine separation.** `async_engine` → FastAPI only; `sync_engine` → Alembic + scripts only. `app/utils/contract_resolver.py` (async) and `scripts/contract_resolver.py` (sync) are distinct modules with distinct caches — never mixed in one process.

11. **Entitlement is serving-layer only, default-deny, dark by default.** Per-client show/hide lives entirely in `app/core/{entitlements,tenancy}.py` + the endpoint gates — never in the pipeline, never a `pl_*` column. `ENTITLEMENTS_ENFORCED` ships **false** (gates are no-ops, unchanged UX); flipping it is a deliberate op gated on grandfathering every existing login onto the `internal` tier first (else default-deny locks them out). New feature = component + endpoint + one entitlement key + assign to tiers in `TIER_TEMPLATES`; **never fork the frontend per tier**. (entitlement-and-tenancy.md.)
